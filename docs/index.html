Agent Sandbox と TypeScript SDK のしくみ

Kubernetes 上で AI エージェント用の隔離実行環境を提供する kubernetes-sigs/agent-sandbox。その 4 つの CRD、Pod 内ランタイム sandboxd、そして TypeScript SDK の内部構造を、図を中心に解説します。

controller v1.0.4 API v1beta1 fork: khirotaka/agent-sandbox @ 7d97d6e

非公式ドキュメントです。TypeScript SDK（agentic-sandbox-client）は khirotaka/agent-sandbox（fork）にのみ存在し、執筆時点で upstream の kubernetes-sigs/agent-sandbox にはマージされていません。API や挙動は予告なく変わる可能性があります。本文はこのリポジトリの submodule が指すコミットのソースコードに基づいています。

この記事は次の 3 つの問いに答えます。

  1. 4 つの CRD（Sandbox / SandboxTemplate / SandboxWarmPool / SandboxClaim）はそれぞれ何を表し、どう連携するのか
  2. sandboxd は Pod の中で何をしているのか
  3. TypeScript SDK は「K8s リソースの管理」と「sandboxd との通信」をどう実装しているのか

1.全体像

Agent Sandbox は、コントロールプレーン（どの Pod をいつ用意するか）とデータプレーン（用意した Pod の中でファイル操作・コマンド実行をする）の 2 つにはっきり分かれています。SDK もこの境界に沿って 2 層に分かれています。

control plane
CRD + コントローラ

「どんな Pod を」「何個温めておき」「誰に割り当てるか」を宣言的に管理する。

data plane
sandboxd

Pod 内で動くデーモン。ファイル API（REST）とプロセス API（gRPC）を提供する。

client
TypeScript SDK

Claim の作成〜Ready 待ち〜削除と、sandboxd への接続・呼び出しを 1 つのハンドルにまとめる。

2.4 つの CRD

CRD は 2 つの API グループに分かれています。コアの agents.x-k8s.io には Sandbox だけがあり、それ単体で「1 つの隔離環境」を表現できます。残りの 3 つは extensions.agents.x-k8s.io にあり、テンプレート化・事前ウォームアップ・払い出しという運用上の仕組みを Sandbox の上に積み上げています。

KindAPI グループひとことで主に誰が作るか
Sandboxagents.x-k8s.io隔離環境 1 つ分（Pod + 任意の Service / PVC）WarmPool / Claim コントローラ（直接作成も可）
SandboxTemplateextensions.agents.x-k8s.ioSandbox の設計図 + NetworkPolicy + Claim に許す上書き範囲プラットフォーム管理者
SandboxWarmPoolextensions.agents.x-k8s.ioテンプレートから Sandbox を N 個事前起動しておくプールプラットフォーム管理者
SandboxClaimextensions.agents.x-k8s.io「プールから 1 つください」という払い出し要求アプリ / SDK

たとえるなら: SandboxTemplate は「クラス定義」、SandboxWarmPool は「事前に温めた ReplicaSet」、SandboxClaim と Sandbox の関係は PersistentVolumeClaim と PersistentVolume の関係に近いものです。利用者は Claim だけを書き、実体（Sandbox）の割り当てはコントローラが行います。

Sandbox（agents.x-k8s.io/v1beta1）

Agent Sandbox の中核となるリソースで、「ステートフルな単一 Pod」を表します。Deployment のように複数レプリカを持つのではなく、1 Sandbox = 1 Pod で、名前・ボリューム・ネットワーク上の識別子が安定していることが特徴です。

フィールド意味
spec.podTemplate作成する Pod の spec とラベル・アノテーション
spec.volumeClaimTemplatesSandbox 用に作る PVC のテンプレート
spec.servicetrue で headless Service（ClusterIP: None）を作成。未指定なら新規作成しない
spec.operatingModeRunning（既定）/ Suspended。Suspended では Pod を止めつつ Sandbox とボリュームは残す
spec.shutdownTime / shutdownPolicy期限到達で Pod と Service を削除。Sandbox 自体は Retain（既定）で残す / Delete で削除
status.conditions[Ready]Pod が実際に Running かつ Ready になって初めて True
status.podIPs / serviceFQDN / nodeName接続先の手がかり。SDK の in-cluster 接続はここを読む

operatingMode は「こうあってほしい」という意図で、実際の状態は Ready 条件で判断します。SDK もこの Ready=True を待ってからハンドルを返します。

SandboxTemplate（extensions.agents.x-k8s.io/v1beta1）

Sandbox の「設計図」です。Sandbox と共通の SandboxBlueprint（podTemplate / volumeClaimTemplates / service）を埋め込み、さらにネットワーク分離とClaim に許す上書きの範囲を定めます。

フィールド既定値意味
networkPolicyManagementManagedManaged ならコントローラがテンプレート単位で共有 NetworkPolicy を 1 つ管理。Unmanaged なら一切作らない（Cilium 等に任せる）
networkPolicy（安全な既定）省略時: Ingress は sandbox-router からのみ、Egress はパブリックインターネットのみ（RFC1918・メタデータサーバ等を遮断）。指定すると既定を丸ごと置き換える
envVarsInjectionPolicyDisallowedClaim の spec.env を許すか（Allowed: 追加のみ / Overrides: 上書きも可）
volumeClaimTemplatesPolicyDisallowedClaim による PVC テンプレートの追加・上書きを許すか

また、テンプレート経由で作られる Pod は automountServiceAccountToken が未指定なら false に補正されます。信頼できないコードを走らせる前提の「secure by default」設計です。

SandboxWarmPool（extensions.agents.x-k8s.io/v1beta1）

コンテナイメージの pull や起動にかかる時間を利用者に見せないため、テンプレートから Sandbox を replicas 個先に起動しておくプールです。プール内の Sandbox は Claim に採用されると所有権が Claim に移り、プールは減った分を自動で補充します。HPA でスケールさせることもできます。

テンプレートが変わったときの古い Sandbox の扱いは updateStrategy で決まります。

  • OnReplenish（既定）: 古い未割り当て Sandbox はそのまま残し、手動削除か Claim による採用で抜けたときに新しいものへ入れ替わる。
  • Recreate: 古い未割り当て Sandbox を即座に削除し、プールを最新テンプレートのものだけにする。

どちらの戦略でも、すでに Claim に割り当て済みの Sandbox には触れません。

SandboxClaim（extensions.agents.x-k8s.io/v1beta1）

アプリ（や SDK）が実際に作成するのはこのリソースです。「どのプールから」「いつまで」使うかを宣言します。

フィールド意味
spec.warmPoolRef.name払い出し元のプール（必須）
spec.lifecycle.shutdownTimeClaim の期限。到達するとコントローラが下位の Sandbox を削除する
spec.lifecycle.shutdownPolicyRetain（既定）/ Delete / DeleteForeground（Sandbox と Pod が消えきるまで Claim を残す）
spec.lifecycle.ttlSecondsAfterFinished終了後に Claim を保持する秒数
spec.additionalPodMetadataPod に伝播するラベル・アノテーション（許可ドメインのみ）
spec.env / spec.volumeClaimTemplatesテンプレートのポリシーが許せば指定可。指定するとウォームプールは使われずコールドスタートになる
status.sandbox.name割り当てられた Sandbox の名前。SDK はまずここを待つ

なぜ env を指定するとコールドスタートになるのか: 環境変数は Pod 作成時に焼き込まれるもので、すでに起動しているプールの Pod に後から注入できないためです。

Claim が Sandbox になるまで

SandboxClaim コントローラは、まず「既存の Sandbox を見つける／プールから採用する」ファストパスを試し、候補がなければテンプレートから新規作成するコールドパスに進みます。

3.sandboxd — Pod 内ランタイムデーモン

sandboxd（packages/sandboxd）は Sandbox Pod の中で動く Go 製のデーモンで、KEP-539.2（runtime standardization）で定義されたポータブルなランタイム API のリファレンス実装です。SDK は sandboxd のバイナリではなく、このワイヤ契約（proto と OpenAPI）に依存しています。

API（gRPC + REST のハイブリッド）

なぜ 2 つのプロトコルを使い分けるのでしょうか。

  • プロセス実行は gRPC — Start は stdout/stderr をプロセス終了まで流し続けるサーバーストリーミング RPC なので、HTTP/2 ストリームが自然。
  • ファイル転送は REST — 中身を protobuf で包まず application/octet-stream の生バイトで送れる。生成スタブなしで curl でも扱える。
ProcessService（gRPC :9090）
RPC種類用途
ExecuteUnary同期実行し stdout / stderr / exit_code をまとめて返す（TS SDK の run() はこれ）
StartServer streamInitEvent → 出力チャンク → ExitEvent をストリーム。PTY 対応
WriteStdinUnary実行中プロセスへ stdin / EOF を送る
SendSignalUnaryプロセスグループへ SIGINT / SIGTERM / SIGKILL
ResizeTTYUnaryPTY のサイズ変更
Filesystem & Runtime REST API（HTTP :8080）
メソッドエンドポイント用途
GET/v1/files/{path}ファイルなら生バイト、ディレクトリなら JSON の一覧
HEAD/v1/files/{path}存在確認（本文なし）
PUT/v1/files/{path}アトミック書き込み。親ディレクトリ自動作成、?mode=0644
DELETE/v1/files/{path}削除。空でないディレクトリは ?recursive=true が必要（なければ 409）
GET/v1/healthReadiness。200 {"status":"ok"}、シャットダウン中は 503
GET/v1/metadataSANDBOX_ 接頭辞の環境変数（認証情報っぽい名前は除外）

内部の仕組み

パスの閉じ込め（path confinement）

ファイル API のパスも、プロセスの cwd も、同じ SanitizePath を通ります。シンボリックリンクを解決した後の実パスがルート配下にあるかを確認するので、../ やシンボリックリンク経由の脱出を防げます。

アトミック書き込み

プロセスの実行と後始末

Execute はコマンドを シェルを介さず argv のまま exec し、Setpgid で独立したプロセスグループに入れます。クライアントのデッドライン切れやキャンセルでコンテキストが終わると、孫プロセスまで含めてプロセスグループごと SIGKILL します（gVisor 向けに /proc を辿るフォールバックもあります）。

デーモン自身が SIGTERM を受けた場合は、管理下のプロセスに SIGTERM → 猶予 → SIGKILL を送ってから HTTP / gRPC サーバーを閉じます。

デプロイ構成（どこでコマンドが走るか）

もっとも重要な事実は、コマンドは sandboxd プロセスが動いているコンテナのルートファイルシステムで実行されるということです。共有ボリュームはファイルを共有しますがバイナリは共有しません。

セキュリティモデル

  • 認証・TLS はしない。port-forward なら apiserver の RBAC（pods/portforward）が認可を担い、Pod ネットワーク経由なら NetworkPolicy やサービスメッシュで保護する。
  • 待受は 0.0.0.0 が既定。封じ込めは loopback バインドではなく Pod 分離と NetworkPolicy で行う。
  • パスの閉じ込めは全ファイルパスと cwd に適用。ただしプロセスのネットワークやファイルシステム全体の隔離は RuntimeClass・securityContext・NetworkPolicy の役目。
  • metadata は接頭辞で許可されたものだけ返し、TOKEN / SECRET / PASSWORD / CREDENTIAL / KEY を含む名前は常に除外。

4.TypeScript SDK（agentic-sandbox-client）

clients/typescript/agentic-sandbox-client は Go / Python クライアントと同じ概念を TypeScript で提供する SDK です（Node.js 22 以上、ESM）。依存は @kubernetes/client-node と ws が必須で、gRPC 用の @bufbuild/protobuf・@connectrpc/connect(-node) は run() を初めて呼んだときに遅延 import される optional peer です。

import { SandboxClient } from "agentic-sandbox-client";

const client = new SandboxClient({ namespace: "default" });
const sandbox = await client.createSandbox("sandboxd-warmpool"); // ← K8s リソース管理層
try {
  await sandbox.files.write("hello.txt", "hi\n");                  // ← sandboxd 通信層 (REST)
  const r = await sandbox.commands.run("cat", ["hello.txt"]);     // ← sandboxd 通信層 (gRPC)
  console.log(r.stdout, r.exitCode);
} finally {
  await sandbox.close();                                          // 接続を閉じて Claim を削除
}

2 層アーキテクチャ

ファイル層責務

sandbox.ts境界Sandbox ハンドル。接続の遅延確立・世代管理、タイムアウト / 中断、close
files.ts / commands.ts公開ファサード公開型だけを使う薄いラッパー。実処理は Sandbox の private 実装に委譲
connection.ts通信接続方式（port-forward / in-cluster-service / in-cluster-pod-ip）の戦略
tunnel.ts通信ローカル TCP ⇔ apiserver の WebSocket port-forward のブリッジ
rest.ts通信REST クライアント（パス検証、サイズ上限、ストリーミング、エラー変換）

trace-manager.ts共通OpenTelemetry（任意）。パスやコマンド文字列は記録しない

K8s リソース管理層

createSandbox(warmpool) は「Claim を作って、割り当てられた Sandbox が Ready になるまで待つ」処理です。この時点では sandboxd にはまだ接続しません。

Watch ループの作り

単に Watch するだけでなく、「GET してから Watch」「Watch が切れたら再 GET」を繰り返します。@kubernetes/client-node 2.x は 30 秒で Watch を打ち切るため、長い待ち時間でも確実に追従できるようにしています。

ハンドルのレジストリと後片付け

  • single-flight: 同じ Claim に対する getSandbox() / createSandbox() の同時呼び出しは 1 つの Promise を共有し、ハンドルが二重にできないようにしている。
  • sandbox.close() は実行中の操作を最大 5 秒待ってから接続を解放し、SandboxClaim を削除する（404 は成功扱い）。closeLocal() は接続だけ解放し Claim は残す。
  • deleteAll() は作成途中の Claim まで含めて掃除する。POST と削除が競合しても、作成直後に気付いてロールバックする。
  • enableAutoCleanup() は SIGINT / SIGTERM / beforeExit で deleteAll() を走らせ、シグナルを再送して終了する。
  • shutdownAfterSeconds を渡すと Claim に絶対時刻の lifecycle.shutdownTime と shutdownPolicy: Delete を設定する。プロセスが落ちてもコントローラが後始末してくれる保険。

sandboxd 通信層

Sandbox ハンドルは、最初に files.* / commands.run() / health() / metadata() が呼ばれた時点で遅延的に接続します。接続一式（トランスポート + REST クライアント + gRPC クライアント）は ConnectionGeneration（世代）としてまとめて扱われ、REST と gRPC は必ず同じ世代のものが使われます。

接続方式（connectivity）

値経路要件向いている場面
"port-forward"（既定）apiserver 経由の WebSocket port-forwardkubeconfig と pods/portforward 権限ラップトップ、CI、クラスタ外全般
"in-cluster-service"headless Service の DNS 名（status.serviceFQDN）へ直接クラスタ内で実行 + テンプレートに service: true + NetworkPolicy で許可クラスタ内のワーカー。信頼境界を越える場合の推奨
"in-cluster-pod-ip"Pod IP（status.podIPs、IPv4 優先）へ直接クラスタ内で実行 + NetworkPolicy で許可Service を作れない場合。IP 再利用のリスクあり

PodTunnel の仕組み（port-forward）

PodTunnel は 127.0.0.1 のランダムポートで REST 用・gRPC 用の 2 つの TCP リスナーを開き、受け付けた TCP 接続 1 本ごとに apiserver への WebSocket を 1 本張って中継します。上位の fetch や Connect-ES からは普通のローカルサーバーに見えるので、HTTP/2（gRPC）もそのまま通ります。

信頼境界: ローカルリスナー自体に認証はありません。接続が開いている間、同じネットワーク名前空間の他プロセスもそのポート経由で sandbox を操作できます。in-cluster モードでは REST / gRPC が平文で Pod ネットワークを流れるので、NetworkPolicy やサービスメッシュで守ってください。

操作の実行とエラー

1 回の呼び出しに何が起きるか

すべてのランタイム呼び出しは runOperation() を通ります。timeoutMs（既定 60 秒）は接続待ちも含めた総予算で、タイムアウト・ハンドルの close・利用者の AbortSignal・世代の無効化を AbortSignal.any() で 1 つにまとめます。

files と commands の違い

sandbox.files.*sandbox.commands.run()
プロトコルREST（Node 組み込み fetch）gRPC Execute（Connect-ES、HTTP/2）
追加依存不要@bufbuild/protobuf, @connectrpc/connect, @connectrpc/connect-node
サイズ上限maxDownloadSize / maxUploadSize（各 256 MiB、ストリーム中に逐次チェック）maxCommandOutputSize（4 MiB、stdout + stderr + protobuf 全体）
入力の扱いルート相対の POSIX パス。絶対パスと .. は送信前に拒否argv そのまま。シェルは挟まない（必要なら run("sh", ["-c", "..."])）
結果Uint8Array / ReadableStream / DirectoryListing など{ stdout, stderr, exitCode }。非 0 の exitCode はエラーではない

6.このリポジトリのデモ

try-agent-sandbox-ts では、同じ SandboxTemplate / WarmPool に対して 2 つの接続方式を試せます。

  • playground（playground/index.ts）: kubeconfig だけで動く。health / metadata、argv 実行、env / cwd、非 0 終了、存在しないコマンド、files の各操作、パス閉じ込め、SandboxClient の一覧・削除 API を一通り試す。
  • sandbox-job（sandbox-job/）: Kubernetes Job として Claim を作り、headless Service 経由で sandboxd に直接つなぐ。テンプレートの networkPolicy が app: sandbox-job からの 8080/9090 だけを許可している点がポイント（既定の NetworkPolicy は sandbox-router しか通さず、router は gRPC を中継できないため）。
task cluster:create    # kind + controller v1.0.4 + sandboxd イメージ + Template/WarmPool
task playground:run    # クラスタ外から port-forward で
task job:run           # クラスタ内から in-cluster-service で
task cluster:delete
