How Agent Sandbox and its TypeScript SDK work

kubernetes-sigs/agent-sandbox provides isolated execution environments for AI agents on Kubernetes. This guide walks through its four CRDs, the in-pod runtime sandboxd, and the internals of the TypeScript SDK, mostly through diagrams.

controller v1.0.4 API v1beta1 fork: khirotaka/agent-sandbox @ 7d97d6e

This is unofficial. The TypeScript SDK (agentic-sandbox-client) lives only in the khirotaka/agent-sandbox fork and, at the time of writing, has not been merged into upstream kubernetes-sigs/agent-sandbox. Its API and behavior may change without notice. Everything here is based on the source at the commit this repository's submodule points to.

This guide answers three questions:

  1. What do the four CRDs (Sandbox / SandboxTemplate / SandboxWarmPool / SandboxClaim) each represent, and how do they fit together?
  2. What does sandboxd do inside the pod?
  3. How does the TypeScript SDK implement "managing K8s resources" and "talking to sandboxd"?

1.The big picture

Agent Sandbox splits cleanly into a control plane (which pod to prepare, and when) and a data plane (file operations and command execution inside that pod). The SDK is split into two layers along the same boundary.

control plane
CRDs + controllers

Declaratively manage what kind of pod to run, how many to keep warm, and who gets one.

data plane
sandboxd

A daemon inside the pod serving a files API (REST) and a process API (gRPC).

client
TypeScript SDK

Wraps claim creation, readiness waiting, deletion, and the sandboxd connection into a single handle.

2.The four CRDs

The CRDs live in two API groups. The core group agents.x-k8s.io contains only Sandbox, which on its own is enough to describe one isolated environment. The other three live in extensions.agents.x-k8s.io and layer the operational machinery on top of Sandbox: templating, pre-warming, and handing sandboxes out.

KindAPI groupIn one lineUsually created by
Sandboxagents.x-k8s.ioOne isolated environment (a Pod plus optional Service / PVCs)The WarmPool / Claim controllers (or directly)
SandboxTemplateextensions.agents.x-k8s.ioBlueprint for a Sandbox + NetworkPolicy + what a claim may overridePlatform admins
SandboxWarmPoolextensions.agents.x-k8s.ioA pool that keeps N sandboxes from a template running in advancePlatform admins
SandboxClaimextensions.agents.x-k8s.ioA request: "give me one from this pool"Apps / the SDK

Analogy: SandboxTemplate is the "class definition", SandboxWarmPool is a "pre-warmed ReplicaSet", and SandboxClaim relates to Sandbox much like a PersistentVolumeClaim relates to a PersistentVolume. Users write only the claim; the controller binds it to an actual Sandbox.

Sandbox (agents.x-k8s.io/v1beta1)

The core resource. It represents a stateful, singleton pod: not a set of replicas like a Deployment, but exactly one pod per Sandbox, with a stable name, storage, and network identity.

FieldMeaning
spec.podTemplateSpec, labels, and annotations for the pod to create
spec.volumeClaimTemplatesTemplates for PVCs created for the sandbox
spec.servicetrue creates a headless Service (ClusterIP: None). When unset, no new Service is created
spec.operatingModeRunning (default) / Suspended. Suspended stops the pod but keeps the Sandbox and its volumes
spec.shutdownTime / shutdownPolicyAt the deadline the pod and service are deleted. The Sandbox itself is kept with Retain (default) or removed with Delete
status.conditions[Ready]True only once the pod is actually Running and Ready
status.podIPs / serviceFQDN / nodeNameWhere to reach it. The SDK's in-cluster modes read these

operatingMode declares intent; the observed state is the Ready condition. The SDK waits for Ready=True before handing back a handle.

SandboxTemplate (extensions.agents.x-k8s.io/v1beta1)

The blueprint for a Sandbox. It embeds the same SandboxBlueprint as Sandbox (podTemplate / volumeClaimTemplates / service) and adds network isolation and how much a claim may override.

FieldDefaultMeaning
networkPolicyManagementManagedManaged: the controller maintains one shared NetworkPolicy per template. Unmanaged: none is created (leave it to Cilium etc.)
networkPolicy(secure default)When omitted: ingress only from the sandbox-router, egress to the public internet only (RFC1918, the metadata server, etc. are blocked). When set, it replaces the defaults entirely
envVarsInjectionPolicyDisallowedWhether a claim may set spec.env (Allowed: add only / Overrides: add and override)
volumeClaimTemplatesPolicyDisallowedWhether a claim may add or override PVC templates

Pods created through a template also get automountServiceAccountToken: false when it isn't set. The design is secure by default, on the assumption that the sandbox runs untrusted code.

SandboxWarmPool (extensions.agents.x-k8s.io/v1beta1)

To hide image pulls and start-up time from users, the pool keeps replicas sandboxes running ahead of time. When a claim adopts one, ownership moves to the claim and the pool automatically replenishes. The pool can also be scaled by an HPA.

What happens to old sandboxes when the template changes is decided by updateStrategy:

  • OnReplenish (default): stale unclaimed sandboxes stay; they are replaced once deleted manually or adopted by a claim.
  • Recreate: stale unclaimed sandboxes are deleted immediately, so the pool only holds sandboxes matching the current template.

Neither strategy ever touches a sandbox already assigned to a claim.

SandboxClaim (extensions.agents.x-k8s.io/v1beta1)

This is what an app (or the SDK) actually creates. It says which pool to draw from and for how long.

FieldMeaning
spec.warmPoolRef.nameThe pool to draw from (required)
spec.lifecycle.shutdownTimeThe claim's deadline. When reached, the controller deletes the underlying Sandbox
spec.lifecycle.shutdownPolicyRetain (default) / Delete / DeleteForeground (the claim stays until its Sandbox and Pod are fully gone)
spec.lifecycle.ttlSecondsAfterFinishedHow long a finished claim is kept
spec.additionalPodMetadataLabels / annotations propagated to the pod (allow-listed domains only)
spec.env / spec.volumeClaimTemplatesAllowed only if the template's policies permit. Setting either skips the warm pool and forces a cold start
status.sandbox.nameThe assigned Sandbox. The SDK waits for this first

Why does setting env force a cold start? Environment variables are baked into a pod when it is created; they cannot be injected into a pool pod that is already running.

From Claim to Sandbox

The SandboxClaim controller first tries a fast path ("find the existing Sandbox, or adopt one from the pool"). Only if there is no candidate does it take the cold path and create a new Sandbox from the template.

3.sandboxd: the in-pod runtime daemon

sandboxd (packages/sandboxd) is a Go daemon that runs inside the sandbox pod. It is the reference implementation of the portable runtime API defined by KEP-539.2 (runtime standardization). The SDKs depend on that wire contract (a proto file and an OpenAPI document), not on the sandboxd binary itself.

API (a gRPC + REST hybrid)

Why two protocols?

  • Process execution uses gRPC. Start is a server-streaming RPC that keeps sending stdout/stderr until the process exits, which maps naturally onto an HTTP/2 stream.
  • File transfer uses REST. File bytes travel as raw application/octet-stream with no protobuf wrapping, and plain curl works without generated stubs.

Internals

Path confinement

Both file API paths and a process's cwd go through the same SanitizePath. It checks that the real path after resolving symlinks is still under the root, which blocks escapes via ../ or symlinks.

Atomic writes

Running and cleaning up processes

Execute execs the command as an argv, with no shell in between, and puts it in its own process group with Setpgid. When the client's deadline passes or it cancels, the context ends and the whole process group, grandchildren included, is SIGKILLed (with a /proc-walking fallback for gVisor).

When the daemon itself receives SIGTERM, it sends SIGTERM to its managed processes, waits a grace period, SIGKILLs any stragglers, and then shuts down the HTTP and gRPC servers.

Deployment topologies (where commands run)

The single most important fact: commands run in the root filesystem of the container hosting the sandboxd process. A shared volume shares files, not binaries.

Security model

  • No authentication, no TLS. With port-forward, the apiserver's RBAC (pods/portforward) authorizes access; over the pod network, protect it with NetworkPolicy or a service mesh.
  • Listens on 0.0.0.0 by default. Containment comes from pod isolation and NetworkPolicy, not from loopback binding.
  • Path confinement applies to every file path and cwd. Isolating a process's network or wider filesystem is the job of RuntimeClass, securityContext, and NetworkPolicy.
  • metadata returns only prefix-allowed names and always withholds names containing TOKEN / SECRET / PASSWORD / CREDENTIAL / KEY.

4.The TypeScript SDK (agentic-sandbox-client)

clients/typescript/agentic-sandbox-client brings the same concepts as the Go and Python clients to TypeScript (Node.js 22+, ESM). @kubernetes/client-node and ws are required dependencies; the gRPC packages @bufbuild/protobuf and @connectrpc/connect(-node) are optional peers imported lazily on the first run().

import { SandboxClient } from "agentic-sandbox-client";

const client = new SandboxClient({ namespace: "default" });
const sandbox = await client.createSandbox("sandboxd-warmpool"); // ← K8s resource layer
try {
  await sandbox.files.write("hello.txt", "hi\n");                  // ← sandboxd layer (REST)
  const r = await sandbox.commands.run("cat", ["hello.txt"]);     // ← sandboxd layer (gRPC)
  console.log(r.stdout, r.exitCode);
} finally {
  await sandbox.close();                                          // close the connection and delete the claim
}

K8s resource layer

createSandbox(warmpool) means "create a claim and wait until its assigned Sandbox is Ready". It does not connect to sandboxd yet.

How the watch loop is built

It doesn't just watch: it GETs, then watches, and GETs again whenever the watch ends. @kubernetes/client-node 2.x aborts every watch after 30 seconds, so this is what lets it follow long waits reliably.

Handle registry and cleanup

  • Single-flight: concurrent getSandbox() / createSandbox() calls for the same claim share one promise, so a claim never ends up with two handles.
  • sandbox.close() waits up to 5 seconds for in-flight work, releases the connection, and deletes the SandboxClaim (404 counts as success). closeLocal() releases only the connection and leaves the claim.
  • deleteAll() also sweeps claims still being created. If a delete races the create POST, the provisioning call notices right after the claim exists and rolls it back.
  • enableAutoCleanup() runs deleteAll() on SIGINT / SIGTERM / beforeExit, then re-raises the signal.
  • shutdownAfterSeconds sets an absolute lifecycle.shutdownTime and shutdownPolicy: Delete on the claim: a safety net so the controller cleans up even if the process dies.

sandboxd communication layer

A Sandbox handle connects lazily, on the first files.* / commands.run() / health() / metadata() call. The whole connection (transport + REST client + gRPC client) is treated as one ConnectionGeneration, and REST and gRPC always come from the same generation.

Connectivity modes

How PodTunnel works (port-forward)

PodTunnel opens two TCP listeners on random 127.0.0.1 ports, one for REST and one for gRPC, and opens one WebSocket to the apiserver for every TCP connection it accepts. To fetch and Connect-ES above it, this looks like an ordinary local server, so HTTP/2 (gRPC) passes straight through.

Trust boundary: the local listeners have no authentication of their own. While the connection is open, any other process in the same network namespace can drive the sandbox through those ports. In the in-cluster modes, REST and gRPC cross the pod network in plaintext, so protect them with a NetworkPolicy or a service mesh.

Operations and errors

What happens on each call

Every runtime call goes through runOperation(). timeoutMs (default 60s) is a total budget that includes waiting on the connect. The timeout, handle close, the caller's AbortSignal, and generation invalidation are merged into one signal with AbortSignal.any().

6.Demos in this repository

try-agent-sandbox-ts exercises both connectivity styles against the same SandboxTemplate / WarmPool.

  • playground (playground/index.ts): needs only a kubeconfig. It exercises health / metadata, argv execution, env / cwd, non-zero exits, a missing executable, every files operation, path confinement, and SandboxClient's list / delete APIs.
  • sandbox-job (sandbox-job/): a Kubernetes Job that creates a claim and talks to sandboxd directly through the headless Service. The key detail is the template's networkPolicy, which admits 8080/9090 only from app: sandbox-job. The default policy admits only the sandbox-router, and the router cannot proxy gRPC.
task cluster:create    # kind + controller v1.0.4 + sandboxd image + Template/WarmPool
task playground:run    # from outside the cluster via port-forward
task job:run           # from inside the cluster via in-cluster-service
task cluster:delete
